# Roadmap — KPI Dashboards, Versioning & KPI Query API

Part of the [AI4SWENG Observability Stack](../README.md) documentation. See the
[documentation index](README.md) for the full set of guides.

Status of the four items requested for the observability platform:

1. Show the D1.1 KPIs and their target levels on the opening dashboard.
2. Add versioning.
3. Let KIO owners (or anyone) fetch historical data through an API, by KIO and
   time interval.
4. Integrate with T3.4.

Normative sources: the **D1.1 Project Management Handbook** (KPIs and targets)
and the **Observability Integration Guide v2.3**
([`report/Observability_v2.3.docx`](report/Observability_v2.3.docx)).

## Decisions that still apply

- **Opening page scope:** the 16 global KPIs (1.1–9.2) only. Work-package and
  task-level KPIs would get their own dashboard if needed.
- **Per-KIO KPI sets follow D1.1 Table 3.** A KIO's dashboard shows only the
  KPIs Table 3 assigns to it. Panels show "—" while no producer reports them;
  they are not hidden.
- **Versioning scope:** what a viewer can see — the stack's version and each
  KIO's version. KPI-catalog and API-contract versioning are out of scope; the
  planned KPI API keeps a `/v1` prefix anyway.
- **Targets live in the repo** (`scripts/d11_kpis.py`) and are baked into the
  generated dashboard JSON. No separate catalog service. If a D1.1 target
  changes, historical attainment is recomputed against the new target.

## Open questions

1. **Table 3 vs D1.1 Table 7.** They disagree on four KIOs:
   - KIO6: Table 7 gives it KPI 9.2; Table 3 gives it none.
   - KIO12: Table 7 gives it KPI 6.2; Table 3 gives it none.
   - KIO3: Table 7 links it to 3.1; Table 3 gives it 1.1 and 1.2.
   - KIO11: Table 7 links it to 3.1 and 7.1; Table 3 gives it 5.1, 6.1 and 6.2.

   With Table 3 as the source, KIO5, KIO6 and KIO12 own no global KPI. This
   needs confirming with the project coordinator.
2. **Which document and revision Table 3 comes from**, so the KPI table can cite
   it.
3. **T3.4 integration direction:** does T3.4 pull KPI history from the API, push
   its own telemetry over OTLP under its own `kio.id` (already covered by the
   current contract), or both?
4. **API exposure:** `/api/metrics` is unauthenticated and meant for a trusted
   network, like the VictoriaMetrics, VictoriaLogs and Tempo ports. If "anyone
   can fetch historical data" comes to mean partners over the internet, auth and
   TLS become a prerequisite.
